N+1 Query Bottleneck Elimination Lab (Lecture 17)

Demonstrates the classic architectural defect: fetching 50 orders in 1 query, then executing 50 separate queries in a loop to fetch line items (51 queries total). Then demonstrates the optimized resolution: 1 single SQL JOIN query with eager aggregation.

Un-Optimized (N+1 Anti-Pattern)

51 Queries Executed

Triggers connection pool thrashing and high network round-trip overhead.

Total Latency: 184.2 ms
Database Roundtrips: 51 Roundtrips
SQL Execution Breakdown:
1x: SELECT * FROM orders WHERE tenant_id = 'tenant_acme' LIMIT 50;
50x: SELECT * FROM order_items WHERE order_id = ?;

Optimized (Single SQL JOIN)

1 Query Executed

Single round-trip eagerly joins orders with all child items in the database engine.

Total Latency: 11.8 ms
Database Roundtrips: 1 Roundtrip
SQL Execution Breakdown:
SELECT o.*, json_agg(oi.*) AS items 
FROM orders o 
LEFT JOIN order_items oi ON o.id = oi.order_id 
WHERE o.tenant_id = 'tenant_acme' 
GROUP BY o.id LIMIT 50;

Strict Multi-Tenant Isolation & Cross-Tenant Boundary Lab (Lecture 18)

Verifies that all database queries and API operations automatically scope to the active tenant. Tenant A must NEVER access Tenant B's data under any circumstance.

Enforced Multi-Tenant Security Standards

  • Tenant Context Discriminator: Every database entity possesses an indexed tenant_id foreign key.
  • Automatic Query Scoping: Data access layer automatically injects WHERE tenant_id = ? into all queries.
  • Strict Boundary Guard: Explicit boundary verification immediately terminates unauthorized access with 403 Forbidden and audit logging.
  • Kafka Message Key Partitioning: Events use tenant_id as partition key, ensuring tenant streams are isolated into dedicated Kafka partitions.
